
Процесс [аутентификации клиента Windows](https://docs.microsoft.com/en-us/windows-server/security/windows-authentication/credentials-processes-in-windows-authentication) включает в себя множество модулей, отвечающих за вход в систему, получение учетных данных и их проверку. Среди различных механизмов аутентификации в Windows Kerberos является одним из наиболее широко используемых и сложных. Локальный орган безопасности ( [Local Security Authority](https://learn.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/configuring-additional-lsa-protection)`LSA` , SID) — это защищенная подсистема, которая аутентифицирует пользователей, управляет локальными входами в систему, контролирует все аспекты локальной безопасности и предоставляет услуги по преобразованию имен пользователей в идентификаторы безопасности (SID).

Подсистема безопасности поддерживает политики безопасности и учетные записи пользователей в компьютерной системе. На контроллере домена эти политики и учетные записи применяются ко всему домену и хранятся в Active Directory. Кроме того, подсистема LSA предоставляет службы для контроля доступа, проверки разрешений и генерации сообщений аудита безопасности.

#### Схема процесса аутентификации Windows

![Диаграмма процесса аутентификации Windows, демонстрирующая взаимодействие между WinLogon.exe, LogonUI, lsass.exe и пакетами аутентификации, такими как NTLM и Kerberos.](https://cdn.services-k8s.prod.aws.htb.systems/content/modules/308/img/Auth_process1.png)

Локальный интерактивный вход в систему осуществляется посредством координации нескольких компонентов: процесса входа в систему ( [WinLogon](https://www.microsoftpressstore.com/articles/article.aspx?p=2228450&seqNum=8) ), процесса пользовательского интерфейса входа в систему ( `LogonUI`), поставщиков учетных данных, службы подсистемы локального управления безопасностью ( `LSASS`), одного или нескольких пакетов аутентификации и либо диспетчера учетных записей безопасности ( `SAM`), либо Active Directory. Пакеты аутентификации в данном контексте представляют собой динамически подключаемые библиотеки (DLL), отвечающие за выполнение проверок аутентификации. Например, для интерактивных входов в систему, не входящих в домен, `Msv1_0.dll`обычно используется пакет аутентификации.

`WinLogon`Это доверенный системный процесс, отвечающий за управление взаимодействиями пользователей, связанными с безопасностью, такими как:

- Запуск `LogonUI`с запросом учетных данных при входе в систему.
- Обработка изменений паролей
- Блокировка и разблокировка рабочей станции

Для получения имени пользователя и пароля WinLogon использует установленные в системе поставщики учетных данных. Эти поставщики учетных данных представляют собой `COM`объекты, реализованные в виде DLL-библиотек.

WinLogon — единственный процесс, который перехватывает запросы на вход в систему с клавиатуры, отправляемые через RPC-сообщения `Win32k.sys`. При входе в систему он немедленно запускает `LogonUI`приложение для отображения графического пользовательского интерфейса. После того, как поставщик учетных данных получает учетные данные пользователя, WinLogon передает их в службу подсистемы локального органа безопасности (Local Security Authority Subsystem Service `LSASS`) для аутентификации пользователя.

#### LSASS

Служба [подсистемы локальной безопасности](https://en.wikipedia.org/wiki/Local_Security_Authority_Subsystem_Service) ( `LSASS`LSASS) состоит из нескольких модулей и управляет всеми процессами аутентификации. Расположенная `%SystemRoot%\System32\Lsass.exe`в файловой системе по адресу [адрес], она отвечает за обеспечение соблюдения локальной политики безопасности, аутентификацию пользователей и пересылку журналов аудита безопасности в [адрес] `Event Log`. По сути, LSASS выступает в роли привратника в операционных системах на базе Windows. Более подробное описание архитектуры LSASS можно найти [здесь](https://docs.microsoft.com/en-us/previous-versions/windows/it-pro/windows-2000-server/cc961760\(v=technet.10\)?redirectedfrom=MSDN) .

Каждый интерактивный сеанс входа в систему создает отдельный экземпляр службы WinLogon. Архитектура [графической идентификации и аутентификации](https://docs.microsoft.com/en-us/windows/win32/secauthn/gina) ( `GINA`GDA) загружается в область обработки, используемую WinLogon, получает и обрабатывает учетные данные и вызывает интерфейсы аутентификации через функцию [LSALogonUser](https://docs.microsoft.com/en-us/windows/win32/api/ntsecapi/nf-ntsecapi-lsalogonuser) .

#### База данных SAM

Диспетчер [учетных записей безопасности](https://docs.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc756748\(v=ws.10\)?redirectedfrom=MSDN) (SAM `SAM`) — это файл базы данных в операционных системах Windows, который хранит учетные данные пользователей. Он используется для аутентификации как локальных, так и удаленных пользователей и использует криптографическую защиту для предотвращения несанкционированного доступа. Пароли пользователей хранятся в виде хешей в реестре, обычно в виде хешей типа `LM`или `NTLM`. Файл SAM находится по адресу `%SystemRoot%\system32\config\SAM`и монтируется в каталог `HKLM\SAM`. Для просмотра или доступа к этому файлу требуются `SYSTEM`права доступа соответствующего уровня.

При настройке системы Windows ее можно отнести либо к рабочей группе, либо к домену. Если система отнесена к рабочей группе, она управляет базой данных SAM локально и хранит всех существующих пользователей локально в этой базе данных. Однако, если система подключена к домену, контроллер домена ( `DC`) должен проверить учетные данные из базы данных Active Directory ( `ntds.dit`), которая хранится в `%SystemRoot%\ntds.dit`.

Для повышения защиты от взлома базы данных SAM в автономном режиме компания Microsoft внедрила в Windows NT 4.0 функцию под названием `SYSKEY`( `syskey.exe`). При включении SYSKEY частично шифрует файл SAM на диске, гарантируя, что хэши паролей для всех локальных учетных записей будут зашифрованы с помощью сгенерированного системой ключа.

#### Менеджер учетных данных

Диспетчер учетных данных — это встроенная функция всех операционных систем Windows, позволяющая пользователям хранить и управлять учетными данными, используемыми для доступа к сетевым ресурсам, веб-сайтам и приложениям. Сохраненные учетные данные хранятся для каждого профиля пользователя в его личном кабинете `Credential Locker`. Учетные данные шифруются и хранятся в следующем месте:

```powershell-session
PS C:\Users\[Username]\AppData\Local\Microsoft\[Vault/Credentials]\
```

Существует несколько методов расшифровки учетных данных, сохраненных с помощью диспетчера учетных данных. В этом модуле мы попрактикуемся на практике с некоторыми из этих методов.

#### НТДС

Очень часто встречаются сетевые среды, где системы Windows подключены к домену Windows. Такая конфигурация упрощает централизованное управление, позволяя администраторам эффективно контролировать все системы в своей организации. В таких средах запросы на вход в систему отправляются контроллерам домена в пределах одного леса Active Directory. Каждый контроллер домена хранит файл с именем `NTDS.dit`, который синхронизируется между всеми контроллерами домена, за исключением [контроллеров домена только для чтения (RODC)](https://docs.microsoft.com/en-us/windows/win32/ad/rodc-and-active-directory-schema) .

`NTDS.dit`Это файл базы данных, в котором хранятся данные Active Directory, включая, помимо прочего:

- Учетные записи пользователей (хеш имени пользователя и пароля)
- Групповые счета
- Компьютерные счета
- Объекты групповой политики

Далее в этом модуле мы рассмотрим методы извлечения учетных данных из `NTDS.dit`файла.
