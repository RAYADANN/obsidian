Стандарт `.well-known`, определенный в [RFC 8615](https://datatracker.ietf.org/doc/html/rfc8615) , служит стандартизированным каталогом в корневом домене веб-сайта. Это выделенное местоположение, обычно доступное по `/.well-known/`пути на веб-сервере, централизует критически важные метаданные веб-сайта, включая файлы конфигурации и информацию, относящуюся к его сервисам, протоколам и механизмам безопасности.

Установление единого места для хранения таких данных `.well-known`упрощает процесс обнаружения и доступа для различных заинтересованных сторон, включая веб-браузеры, приложения и инструменты безопасности. Такой упрощенный подход позволяет клиентам автоматически находить и получать определенные файлы конфигурации, формируя соответствующий URL-адрес. Например, для доступа к политике безопасности веб-сайта клиент запросит `https://example.com/.well-known/security.txt`.

( ) ведет [реестр](https://www.iana.org/assignments/well-known-uris/well-known-uris.xhtml) URI , каждый из которых служит определенной цели `Internet Assigned Numbers Authority`, определяемой различными спецификациями и стандартами. ## Web Recon и .well-known

В веб-разведке `.well-known`URI могут оказаться бесценными для обнаружения конечных точек и деталей конфигурации, которые можно дополнительно проверить в ходе тестирования на проникновение. Один из особенно полезных URI — `openid-configuration`.

URI `openid-configuration`является частью протокола OpenID Connect Discovery, уровня идентификации, построенного поверх протокола OAuth 2.0. Когда клиентское приложение хочет использовать OpenID Connect для аутентификации, оно может получить конфигурацию поставщика OpenID Connect, обратившись к `https://example.com/.well-known/openid-configuration`конечной точке. Эта конечная точка возвращает JSON-документ, содержащий метаданные о конечных точках поставщика, поддерживаемых методах аутентификации, выдаче токенов и многом другом:

        json
`{   "issuer": "https://example.com",  "authorization_endpoint": "https://example.com/oauth2/authorize",  "token_endpoint": "https://example.com/oauth2/token",  "userinfo_endpoint": "https://example.com/oauth2/userinfo",  "jwks_uri": "https://example.com/oauth2/jwks",  "response_types_supported": ["code", "token", "id_token"],  "subject_types_supported": ["public"],  "id_token_signing_alg_values_supported": ["RS256"],  "scopes_supported": ["openid", "profile", "email"] }`

Информация, полученная с `openid-configuration`конечной точки, предоставляет множество возможностей для исследования:

1. `Endpoint Discovery`:
    - `Authorization Endpoint`: Определение URL-адреса для запросов авторизации пользователя.
    - `Token Endpoint`: Определение URL-адреса, по которому выдаются токены.
    - `Userinfo Endpoint`Определение местоположения конечной точки, предоставляющей информацию о пользователе.
2. `JWKS URI`: Здесь `jwks_uri`отображается `JSON Web Key Set`( `JWKS`), содержащая подробную информацию о криптографических ключах, используемых сервером.
3. `Supported Scopes and Response Types`Понимание того, какие области действия и типы ответов поддерживаются, помогает определить функциональность и ограничения реализации OpenID Connect.
4. `Algorithm Details`Информация о поддерживаемых алгоритмах подписи может иметь решающее значение для понимания применяемых мер безопасности.

Изучение [реестра IANA](https://www.iana.org/assignments/well-known-uris/well-known-uris.xhtml) и экспериментирование с различными `.well-known`URI — бесценный подход к выявлению дополнительных возможностей для веб-разведки. Как показано на примере `openid-configuration`приведенной выше конечной точки, эти стандартизированные URI обеспечивают структурированный доступ к важным метаданным и деталям конфигурации, позволяя специалистам по безопасности всесторонне составить карту безопасности веб-сайта.
