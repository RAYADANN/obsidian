
Эта категория фокусируется на критических ошибках, когда приложение доверяет коду или данным без проверки их подлинности. В 2021 году сюда включили и **Insecure Deserialization** (небезопасную десериализацию).

---

### **1. Общее описание**

Уязвимость возникает, когда инфраструктура или код полагаются на данные, которые могут быть подменены атакующим. Это касается как обновлений ПО (Software Integrity), так и передачи сложных объектов данных (Data Integrity).

**Основные сценарии:**

- **Небезопасная десериализация:** Приложение восстанавливает объект из строки (JSON, XML, бинарный формат), присланной пользователем, выполняя при этом скрытый код.
    
- **Атаки на цепочку поставок (Supply Chain Attacks):** Использование обновлений из недоверенных репозиториев без проверки цифровой подписи.
    
- **CI/CD Pipeline Security:** Возможность внедрения вредоносного кода в процесс сборки приложения.
    

---

### **2. Почему это возникает? (Корневые причины)**

- **Доверие к источнику:** Разработчики считают, что если данные пришли из их собственной базы или через куки, они безопасны.
    
- **Автоматизация без проверок:** Системы автоматически скачивают и устанавливают плагины/библиотеки, проверяя только версию, но не автора.
    
- **Сложность форматов:** Библиотеки для работы с форматами вроде Java RMI, Python Pickle или PHP Serialization позволяют передавать не просто данные, а целые инструкции по их обработке.
    

---

### **3. Методология поиска (Как искать пентестеру)**

- **Анализ трафика на сериализованные объекты:**
    
    - **Java:** Ищи строки, начинающиеся с `rO0` (Base64 от `AC ED 00 05` — магические байты Java-сериализации).
        
    - **Python:** Ищи данные, похожие на вывод модуля `pickle`.
        
    - **PHP:** Ищи строки вида `O:4:"User":2:{...}` в куках или POST-запросах.
        
- **Проверка механизмов обновления:**
    
    - Проверь, качаются ли обновления по HTTP.
        
    - Попробуй подменить файл обновления и посмотри, установит ли его система без ошибки "Signature mismatch".
        
- **Анализ манифестов сборки:**
    
    - Проверка `package.json` или `go.mod` на использование библиотек из сторонних, не официальных репозиториев.

### **4. Как эксплуатировать (Примеры)**

#### **Пример 1: Python Pickle RCE**

Приложение хранит настройки сессии в куках, сериализованных через pickle.

Эксплойт: Хакер создает объект, который при десериализации (функция __reduce__) выполняет системную команду:

Python

```
import pickle, os
class Exploit(object):
    def __reduce__(self):
        return (os.system, ('cat /etc/passwd',))
```

Сервер десериализует куку и выполняет команду `cat /etc/passwd`.

#### **Пример 2: Атака на обновление (SolarWinds style)**

Атакующий взламывает сервер сборки компании (CI/CD).

Эксплойт: Он внедряет вредоносный код в официальное обновление программы. Клиенты скачивают «легальное» обновление с цифровой подписью компании, но внутри него уже сидит бэкдор.

#### **Пример 3: JWT без подписи**

Приложение использует JSON Web Tokens, но не проверяет подпись (алгоритм none).

Эксплойт: Хакер меняет в JWT-токене user: "guest" на user: "admin" и отправляет обратно. Сервер верит данным на слово.

### **5. Инструменты для поиска**

|**Инструмент**|**Функция**|
|---|---|
|**ysoserial (Java/JS/C#)**|Коллекция готовых "гаджетов" (payloads) для эксплуатации десериализации.|
|**Pickle-inspector**|Анализ опасных инструкций внутри Python Pickle файлов.|
|**Burp Suite (Insecure Deserialization Scanner)**|Автоматический поиск сериализованных данных в запросах.|
|**Gittyleaks / TruffleHog**|Поиск секретов, которые могли утечь и позволить подделать подпись данных.|

---

### **6. Как исправить (Рекомендации разработчику)**

1. **Используйте простые форматы:** Перейдите на JSON или XML (без внешних сущностей). Они передают только данные, а не исполняемые объекты.
    
2. **Цифровая подпись:** Всегда подписывайте данные (например, через HMAC) перед отправкой клиенту. При получении проверяйте, не изменилась ли подпись.
    
3. **Изоляция десериализации:** Если десериализация необходима, запускайте её в среде с минимальными привилегиями (Sandboxing), где запрещен доступ к сети и файловой системе.
    
4. **Проверка зависимостей:** Используйте только официальные репозитории и проверяйте хеш-суммы (checksums) скачанных пакетов.
    
5. **Контроль CI/CD:** Защищайте доступ к серверам сборки (Jenkins, GitLab CI) так же строго, как и к боевым серверам.
