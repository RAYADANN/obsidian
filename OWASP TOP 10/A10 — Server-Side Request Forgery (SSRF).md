
Это одна из самых «умных» и опасных атак. Она позволяет хакеру использовать уязвимый сервер в качестве **прокси-сервера** для атаки на внутренние ресурсы, которые обычно закрыты от внешнего мира.

---

### **1. Общее описание**

**SSRF (Подделка запроса со стороны сервера)** — это ситуация, когда злоумышленник заставляет серверное приложение сделать HTTP-запрос (или любой другой запрос) на произвольный адрес, выбранный атакующим.

Представь: ты стоишь перед закрытой дверью (внутренняя сеть компании). Но рядом есть окно (веб-сервер), который может общаться с тем, кто за дверью. Ты передаешь записку через окно, и сервер послушно передает её внутрь.

**Основные сценарии:**

- **Сканирование внутренней сети:** Сервер «прощупывает» порты других серверов внутри дата-центра.
    
- **Доступ к метаданным облака:** Получение секретных ключей в AWS, GCP или Azure.
    
- **Чтение локальных файлов:** Использование протоколов типа `file:///`.
    

---

### **2. Почему это возникает? (Корневые причины)**

- **Функции импорта по URL:** Возможность загрузить аватарку по ссылке, предпросмотр новостей по ссылке или импорт данных из стороннего API.
    
- **Отсутствие валидации:** Приложение принимает URL от пользователя и сразу делает по нему запрос, не проверяя, ведет ли он на «белый список» сайтов.
    
- **Доверие внутренней сети:** Многие разработчики не ставят пароли на базы данных (Redis, MongoDB) или внутренние панели управления, считая, что «из интернета сюда всё равно никто не зайдет».
    

---

### **3. Методология поиска (Как искать пентестеру)**

- **Поиск параметров с URL:**
    
    - Ищи в запросах ключи типа `?url=`, `?link=`, `?dest=`, `?image=`, `?api=`.
        
- **Тестирование на Loopback (localhost):**
    
    - Попробуй подставить `http://127.0.0.1:80` или `http://localhost:22`. Если ответ сервера изменился или пришла ошибка «Connection refused», сервер пытается достучаться сам до себя.
        
- **Слепой SSRF (Blind SSRF):**
    
    - Укажи адрес своего сервера (например, через Burp Collaborator). Если твой сервер зафиксировал входящее соединение от сервера приложения — уязвимость подтверждена.
        
- **Использование других протоколов:**
    
    - Попробуй `file:///etc/passwd` (чтение файлов).
        
    - Попробуй `dict://localhost:11211/` (общение с Memcached).
        
    - Попробуй `gopher://` (универсальный протокол для атак на внутренние сервисы).
        

---

### **4. Как эксплуатировать (Примеры)**

#### **Пример 1: Кража ключей из облака (AWS)**

Большинство облачных провайдеров имеют внутренний сервис метаданных по адресу 169.254.169.254.

Эксплойт: Хакер отправляет запрос ?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/admin-role.

Сервер возвращает временные ключи доступа (AccessKeyId, SecretAccessKey), с помощью которых хакер может управлять всем облаком компании через свой компьютер.

#### **Пример 2: Доступ к административной панели**

Внутренняя панель мониторинга доступна только с 127.0.0.1:8080.

Эксплойт: Хакер через SSRF запрашивает http://127.0.0.1:8080/admin/delete_user?id=1. Сервер думает, что запрос пришел от «самого себя», и послушно удаляет пользователя.

#### **Пример 3: Сканирование внутренней сети**

Хакер перебирает IP в локальной сети через SSRF: `192.168.1.1`, `192.168.1.2`... Если ответ на запрос `192.168.1.5:5432` пришел быстрее, чем на другие, значит, там живет база PostgreSQL.

### **5. Инструменты для поиска**

|**Инструмент**|**Функция**|
|---|---|
|**Burp Collaborator**|Незаменим для обнаружения Blind SSRF (когда сервер делает запрос, но не показывает результат тебе).|
|**SSRFmap**|Автоматизированный инструмент для поиска и эксплуатации SSRF через различные протоколы.|
|**Interactsh**|Аналог Burp Collaborator для командной строки.|

### **6. Как исправить (Рекомендации разработчику)**

1. **Белые списки (Allow-lists):** Разрешайте делать запросы только на конкретные домены (например, `api.google.com`). Всё остальное — блокировать.
    
2. **Запрет локальных адресов:** На уровне кода запретите запросы к `127.0.0.1`, `localhost`, `169.254.x.x` и всей подсети `192.168.x.x`.
    
3. **Сетевая изоляция (Firewall):** Настрой сетевой экран (iptables или правила облака) так, чтобы веб-сервер вообще не мог инициировать соединения с внутренней сетью (кроме тех, что жизненно необходимы).
    
4. **Отключение ненужных протоколов:** Разрешите только `http://` и `https://`. Отключите поддержку `file://`, `gopher://`, `ftp://` в библиотеках (например, в cURL).
    
5. **Не доверяйте ответам:** Не возвращайте пользователю «сырой» ответ от стороннего ресурса.
