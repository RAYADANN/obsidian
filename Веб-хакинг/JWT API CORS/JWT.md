**JWT (JSON Web Token)** — это современный стандарт передачи информации между клиентом и сервером в виде компактного JSON-объекта. Его главная фишка в том, что он **самодостаточен**: серверу не нужно хранить данные о твоей сессии в базе, вся информация уже «зашита» в самом токене.

Давай разберем его по частям, как настоящий пентестер.

---

### **1. Анатомия JWT**

Токен всегда состоит из трех частей, разделенных точками (например, `aaaaa.bbbbb.ccccc`), закодированных в **Base64URL**.

#### **A. Header (Заголовок)**

Здесь указан тип токена и алгоритм подписи.

JSON

```
{
  "alg": "HS256",
  "typ": "JWT"
}
```

#### **B. Payload (Полезная нагрузка)**

Здесь лежат данные (claims). Это то, что мы хотим передать.

JSON

```
{
  "sub": "1234567890",
  "name": "Ivan",
  "role": "user",
  "iat": 1516239022
}
```

#### **C. Signature (Подпись)**

Самая важная часть. Она создается так: берется Header и Payload, склеиваются, и хешируются с помощью секретного ключа, который знает только сервер. Если изменить хотя бы один символ в Payload, подпись перестанет совпадать, и сервер поймет, что токен подделан.

---

### **2. Главные векторы атак на JWT**

Когда ты видишь JWT в заголовке `Authorization: Bearer <token>`, твоя задача — проверить сервер на «доверчивость».

#### **Атака 1: Алгоритм "None"**

Это классика. Хакер меняет заголовок на `"alg": "None"`.

- **Логика:** Некоторые библиотеки JWT при виде `alg: None` просто перестают проверять подпись.
    
- **Что делать:** Ты меняешь в Payload `role: user` на `role: admin`, убираешь третью часть токена (подпись) совсем и отправляешь запрос. Если сервер пустил — это критический баг.
    

#### **Атака 2: Изменение алгоритма (RS256 на HS256)**

- **RS256** — асимметричный алгоритм (нужен приватный ключ для подписи и публичный для проверки).
    
- **HS256** — симметричный (один и тот же ключ для всего).
    
- **Хитрость:** Атакующий меняет в заголовке `RS256` на `HS256` и подписывает токен **публичным ключом** сервера (который часто висит в открытом доступе). Сервер, думая, что он в режиме HS256, проверяет подпись своим же публичным ключом и «съедает» токен.
    

#### **Атака 3: Слабый секретный ключ (Brute Force)**

Если используется HS256, то подпись зависит от секретной строки. Если админ поставил ключ типа `123456` или `secret`, его можно подобрать.

- **Инструмент:** `hashcat` или специальный скрипт `jwt-cracker`.
    

---

### **3. Как это выглядит в жизни (Практика)**

Представь, ты перехватил токен в **Burp Suite**. Он выглядит как каша из букв: `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6NDIsImFkbWluIjpmYWxzZX0...`

1. Заходишь на сайт **jwt.io** (инструмент №1 для анализа).
    
2. Вставляешь токен. В левой части он расшифруется в обычный JSON.
    
3. Видишь: `"admin": false`.
    
4. Меняешь на `"admin": true`.
    
5. Теперь самое сложное: если сервер проверяет подпись правильно, твой новый токен будет отклонен. Но если там есть одна из ошибок выше (alg: none или слабый ключ) — ты победил.
    

---

### **4. Почему JWT — это НЕ шифрование?**

Это самая частая ошибка новичков. **Base64 — это не шифрование, это просто способ записи.** Любой человек, перехвативший JWT, может прочитать всё, что написано в Payload.

> **Золотое правило:** Никогда не клади в JWT пароли или номера карт. Только ID пользователя, роли и сроки действия.
