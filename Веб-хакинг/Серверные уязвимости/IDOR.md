**IDOR (Insecure Direct Object Reference)** — это «уязвимость здравого смысла». В отличие от сложных SQL-инъекций, здесь не нужно быть программистом, чтобы понять суть. Это ошибка в логике доступа, когда сервер доверяет пользователю на слово.

---

### **1. Суть уязвимости: «А что, если...»**

Представь камеру хранения на вокзале. Ты подходишь к терминалу, вводишь номер своей ячейки **105**, и она открывается. Но что, если ты введешь **106**? Если терминал не проверит твой билет (токен доступа), он просто откроет чужую ячейку. Это и есть IDOR.

В веб-приложениях «номер ячейки» — это обычно ID в адресной строке или в теле запроса.

---

### **2. Как это выглядит на практике?**

Допустим, ты зашел в личный кабинет соцсети, чтобы отредактировать свой профиль. Твой браузер отправляет такой запрос:

`GET /api/v1/get_user_info?id=775`

Сервер видит ID `775`, находит его в базе и отдает твои данные (телефон, адрес, почту).

**Действия хакера:**

1. Он меняет `775` на `774`.
    
2. Если разработчик не прописал проверку: _«А принадлежит ли профиль 774 тому, кто сейчас отправил запрос?»_, сервер послушно отдаст данные пользователя №774.
    

---

### **3. Где искать IDOR?**

IDOR может прятаться везде, где используются идентификаторы:

- **URL-параметры:** `site.com/invoice/pdf/4567` (скачивание счетов).
    
- **Тело POST-запроса:** При смене пароля или почты отправляется `{"user_id": 123, "new_password": "..."}`. Если поменять `user_id`, можно сменить пароль другому человеку.
    
- **Cookies:** Иногда ID сессии или пользователя хранится в куках в открытом виде: `user_id=123`.
    
- **API-запросы:** Современные мобильные приложения часто общаются с сервером через JSON-запросы, где IDOR встречается постоянно.
    

---

### **4. Почему это происходит? (Разбор «под капотом»)**

Ошибка всегда в коде бэкенда. Разработчик делает так (плохой пример на языке Python/Flask):

Python

```
@app.route('/view_document')
def view_document():
    doc_id = request.args.get('id')
    # Сервер просто ищет документ по ID и отдает его
    document = db.find_one({'id': doc_id}) 
    return jsonify(document)
```

**Как должно быть (хороший пример):**

Python

```
@app.route('/view_document')
def view_document():
    doc_id = request.args.get('id')
    current_user = get_session_user() # Узнаем, кто делает запрос
    
    # Сервер ищет документ, который принадлежит ИМЕННО этому пользователю
    document = db.find_one({'id': doc_id, 'owner': current_user}) 
    
    if not document:
        return "Доступ запрещен", 403
    return jsonify(document)
```

---

### **5. Как пентестеры ищут IDOR?**

1. **Создают два аккаунта** (User A и User B).
    
2. Заходят под User A и находят запрос, где фигурирует его ID (например, `id=100`).
    
3. Копируют этот запрос в **Burp Suite**.
    
4. Меняют `id=100` на `id` пользователя B.
    
5. Если сервер отдал данные пользователя B — **Bingo!** Это критическая уязвимость.
    

---

### **6. Усложненные IDOR: Не только цифры**

Иногда ID — это не просто `1, 2, 3`, а длинная строка (UUID или хэш), например: `id=6eb8-4f2a-8c9d`. Такой ID невозможно угадать перебором. Однако, если хакер может найти этот UUID в другом месте (например, в публичном профиле пользователя или в исходном коде страницы), это всё равно будет IDOR.

---

### **Как защититься?**

- **Никогда не доверяйте ID от клиента.** Всегда проверяйте права доступа на стороне сервера.
    
- **Используйте непредсказуемые ID (UUID).** Это не лечит саму дыру, но делает её эксплуатацию почти невозможной.
    
- **Централизованная проверка.** Лучше иметь одну функцию «Проверки прав», через которую проходят все запросы.
