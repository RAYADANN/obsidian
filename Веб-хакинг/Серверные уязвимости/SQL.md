**SQL-инъекция (SQLi)** — это, пожалуй, самая «классическая» и опасная уязвимость веб-приложений. Она позволяет атакующему вмешаться в запросы, которые приложение делает к своей базе данных.

Если провести аналогию: представь, что ты заполняешь анкету в банке. В графе «Имя» ты пишешь: _«Иван. А также переведите все деньги с этого счета на мой»_. Если клерк (сервер) просто прочитает это как одну команду и исполнит — это и есть инъекция.

---

### **1. Механика: Почему это происходит?**

Проблема кроется в **неправильной конкатенации (склеивании) строк**. Разработчик пишет код, который берет ввод пользователя и вставляет его прямо в «тело» SQL-запроса.

**Пример кода (уязвимый PHP):**

PHP

```
$id = $_GET['id'];
$query = "SELECT name, email FROM users WHERE id = " . $id;
```

Если ты введешь `id=1`, сервер выполнит: `SELECT name, email FROM users WHERE id = 1`. Все честно.

Но если хакер введет `1 OR 1=1`, запрос превратится в: `SELECT name, email FROM users WHERE id = 1 OR 1=1`. Поскольку `1=1` — это всегда правда, база данных вернет **всех** пользователей из таблицы.

### **2. Основные виды SQL-инъекций**

Пентестеры делят SQLi на три большие группы в зависимости от того, как хакер получает ответ:

#### **A. In-band (Классические)**

Данные извлекаются через тот же канал, что и запрос.

- **Error-based:** Мы специально портим запрос (например, ставим лишнюю кавычку `'`), чтобы сервер выдал ошибку. В тексте ошибки часто можно увидеть структуру базы или версии софта.
    
- **Union-based:** Используется оператор `UNION`, чтобы склеить результат основного запроса с результатом нашего «злого» запроса. Так можно вывести на экран список паролей прямо в профиле пользователя.
    

#### **B. Inferential (Слепые / Blind)**

Сервер не выдает ошибок и не показывает данные базы на странице. Он просто говорит «ОК» или «Ошибка».

- **Boolean-based:** Мы задаем вопросы «да/нет». Например: _«Если первая буква пароля админа — 'A', то загрузи страницу нормально»_. Если страница загрузилась — мы угадали букву.
    
- **Time-based:** Мы заставляем сервер «подвиснуть». _«Если версия базы 5.7, подожди 10 секунд перед ответом»_. Если сайт долго грузится — условие верно.
    

#### **C. Out-of-band**

Самый редкий вид. Хакер заставляет сервер отправить данные на внешний сервер (например, через DNS-запрос или HTTP).

### **3. Анатомия атаки (Пошагово)**

Допустим, у нас есть сайт `shop.com/product.php?id=10`.

1. **Поиск точки входа:** Добавляем кавычку `'` к ID. Если страница выдала ошибку базы — уязвимость есть.
    
2. **Определение количества колонок:** Используем `ORDER BY`. Если `ORDER BY 3` работает, а `ORDER BY 4` выдает ошибку — значит, в таблице 3 колонки.
    
3. **Вывод данных:** Используем `UNION SELECT 1,2,database()`. Вместо товара на странице отобразится название базы данных.
    
4. **Сбор «урожая»:** Узнаем названия таблиц, колонок и, наконец, выгружаем хеши паролей из таблицы `users`.

### **4. Как защититься? (Для разработчика)**

Единственный надежный способ — **Prepared Statements (Подготовленные выражения)**.

Вместо того чтобы склеивать строки, мы отправляем базе «шаблон» запроса отдельно, а данные пользователя — отдельно. База данных воспринимает пользовательский ввод **только как текст**, а не как часть команды.

**Правильный код (PDO в PHP):**

PHP

```
$stmt = $pdo->prepare('SELECT name FROM users WHERE id = :id');
$stmt->execute(['id' => $id]); // Теперь ввод в $id не может изменить логику SQL
```

### **5. Инструментарий**

- **sqlmap:** «Король» инструментов. Автоматический сканер, который сам находит и эксплуатирует SQL-инъекции. Он может выгрузить всю базу за считанные минуты.
    
- **Burp Suite:** Позволяет вручную менять параметры запроса и смотреть, как меняется ответ сервера.
