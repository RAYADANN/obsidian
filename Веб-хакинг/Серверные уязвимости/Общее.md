Серверные уязвимости (Backend-уязвимости) — это ошибки в коде или конфигурации сервера, которые позволяют атакующему вмешаться в работу приложения, украсть данные из базы или даже полностью захватить управление сервером.

Чтобы понимать их «на молекулярном уровне», нужно помнить: **почти любая серверная уязвимость — это результат того, что сервер доверяет входным данным от пользователя.**

Давай разберем «большую тройку» самых опасных серверных уязвмиостей.

---

### **1. SQL-инъекции (SQL Injection / SQLi)**

**Что это?** Атака, при которой хакер вставляет свой вредоносный код в SQL-запрос к базе данных.

- **Почему это происходит:** Разработчик берет данные из запроса (например, логин) и просто «склеивает» их с SQL-командой.
    
- **Как это работает:** Представь запрос на вход: `SELECT * FROM users WHERE username = '$user' AND password = '$password'`. Хакер вместо логина вводит: `' OR 1=1 --`. Запрос превращается в: `SELECT * FROM users WHERE username = '' OR 1=1 -- ' AND password = '...'`. Условие `1=1` всегда верно, а символы `--` превращают остаток запроса в комментарий. Сервер пускает хакера без пароля.
    
- **Опасность:** Кража всей базы данных (логины, пароли, карты), удаление данных.
    

---

### **2. IDOR (Insecure Direct Object Reference)**

**Что это?** Небезопасная прямая ссылка на объект. Это самая частая логическая ошибка.

- **Почему это происходит:** Сервер выдает файл или данные только на основании ID, не проверяя, имеет ли текущий пользователь право доступа к этому ID.
    
- **Как это работает:** Ты залогинился и скачиваешь свой счет: `https://bank.com/download_receipt?id=1500`. Ты просто меняешь `id=1500` на `id=1499`. Если сервер не проверяет «владельца» чека №1499, он просто отдаст тебе чужой документ.
    
- **Опасность:** Массовая утечка персональных данных через простой перебор цифр в скрипте.
    

---

### **3. RCE (Remote Code Execution)**

**Что это?** Самая страшная уязвимость — «Удаленное выполнение кода». Она позволяет хакеру запускать любые команды прямо в операционной системе сервера.

- **Почему это происходит:** Сервер использует функции, которые исполняют системные команды (например, `exec()` в PHP или `system()` в Python), и передает туда данные от пользователя без фильтрации.
    
- **Как это работает:** Сайт предлагает проверить пинг до твоего IP. Внутри сервера работает команда: `ping -c 3 [твой_ввод]`. Ты вводишь: `8.8.8.8 ; cat /etc/passwd`. Точка с запятой в Linux разделяет команды. Сервер сначала пропингует Google, а потом **покажет тебе файл со списком всех пользователей системы**.
    
- **Опасность:** Полный захват сервера (создание своих пользователей, установка вирусов, использование сервера для атак на другие компании).
    

---

### **4. SSRF (Server-Side Request Forgery)**

**Что это?** Подделка запроса со стороны сервера. Хакер заставляет сервер отправить запрос туда, куда самому хакеру доступа нет.

- **Почему это происходит:** Сервер умеет скачивать данные по ссылке (например, загрузка картинки из интернета по URL).
    
- **Как это работает:** Сайт просит: «Введи ссылку на аватарку». Хакер вводит: `http://localhost:8080/admin_panel`. Поскольку запрос идет **внутри** сети сервера, он может обойти фаерволы и попасть во внутренние админки или базы данных, которые закрыты от внешнего интернета.
    
- **Опасность:** Доступ к внутренней инфраструктуре компании, кража секретных ключей облачных сервисов (AWS/Google Cloud).
    

---

### **Как защититься? (Золотые правила)**

1. **Никогда не доверяй пользователю.** Все данные (из форм, ссылок, куки) должны проверяться.
    
2. **Используй подготовленные выражения (Prepared Statements).** Это единственный надежный способ победить SQL-инъекции (данные отделяются от команд).
    
3. **Принцип минимальных привилегий.** Веб-сервер не должен работать под правами администратора (root). Если его взломают через RCE, ущерб будет ограничен.
    
4. **Белые списки.** Если нужно запускать команды, проверяй ввод по списку разрешенных символов или слов.
